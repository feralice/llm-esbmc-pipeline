## Roteiro de evolução discutido (não é hoje, é direção futura)

Comparado a um roteiro que a usuária trouxe (fluxo com loop de feedback
counterexample→LLM), o que já existe vs. o que falta:

**Já existe**: AST extrai fatos (`ast_utils.py`), LLM gera hipótese
estruturada (`llm/findings.py`), LLM gera harness (driver tier), ESBMC
verifica, retry técnico do harness (`synth_retries`), separação bug vs.
code smell (`finding_type="smell_heuristic"` nunca vai pro ESBMC), scan de
repositório inteiro (modo `scan`, função por função).

**Falta de verdade** (evolução real, não conserto):
- Contraexemplo do ESBMC virar **explicação em linguagem natural** pra
  LLM (hoje só volta pra consertar sintaxe do harness, não pra explicar o
  bug com os valores concretos).
- LLM refinar a **hipótese** (categoria/expressão), não só o harness.
- Roteamento custo-benefício SLM barato → LLM caro por dificuldade do
  caso (não existe ainda).
- Comparado ao paper Faria et al. 2026 (Dafny, LLM+teste como oráculo,
  citação verificada hoje via arXiv 2601.12845): usar teste real do
  BugsInPy como oráculo em vez de assert inventado pela LLM. Só serve pro
  benchmark controlado (bug já catalogado com teste); não generaliza pra
  varredura selvagem de repo desconhecido — pra isso, o validador
  diferencial (item 1 acima) é o que generaliza.
