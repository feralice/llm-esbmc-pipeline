[LADO ESQUERDO — CONTEXTO]

Por que Python é difícil de analisar automaticamente?

• Python é a linguagem #1 no índice TIOBE (janeiro 2026) [TIOBE, 2026]
• Amplamente usada em web, ciência de dados e IA
• Tipagem dinâmica → variáveis mudam de tipo em tempo de execução
  ↳ dificulta prever o comportamento sem executar o programa
• Ferramentas tradicionais (lint, mypy) não detectam falhas executáveis
  como divisão por zero ou acesso fora dos limites [Farias et al., 2024]

[LADO DIREITO — O PROBLEMA]

Duas ferramentas existem — nenhuma é suficiente sozinha

┌───────────────────────────────────────────────────────────────┐
│  LLMs para código (GPT, Claude, Gemini, DeepSeek, Qwen)       │
│  ✓ Identificam padrões suspeitos em segundos (2–10s/função)   │
│  ✓ Cobrem bugs executáveis E problemas de qualidade           │
│  ✗ Produzem falsos positivos — alerta sem bug real            │
│  ✗ Produzem alucinações — citam operações que não existem     │
│  ✗ Sem garantia formal — resultado é uma SUSPEITA             │
│                                                               │
│  Benchmark PrimeVul [Ding et al., 2025]:                      │
│  F1 = apenas 3,09% em vulnerabilidades reais                  │
├───────────────────────────────────────────────────────────────┤
│  ESBMC-Python (verificador formal baseado em BMC)             │
│  ✓ Confirma bugs com contraexemplos CONCRETOS                 │
│  ✓ Precisão máxima: quando acusa, é real                      │
│  ✓ Verifica Python diretamente, sem traduzir para C           │
│  ✗ Não faz triagem — precisa ser direcionado manualmente      │
│  ✗ Não confirma code smells — não são propriedades formais    │
│  ✗ Custo alto: 35–50 segundos por função [Shivaji et al., 2026]│
└───────────────────────────────────────────────────────────────┘

→ Precisamos combinar as duas abordagens.

Referências: [TIOBE, 2026]; [Farias et al., 2024]; [Ding et al., 2025];
             [Ullah et al., 2024]; [Shivaji et al., 2026]

Questão de pesquisa:

  "Como combinar modelos de linguagem para código e verificação formal
   para aumentar a confiabilidade da detecção automática de defeitos em
   programas Python, reduzindo falsos positivos e diferenciando bugs
   executáveis de code smells?"

Objetivos específicos:

  1. Construir dataset de 70 funções Python com ground truth manual
     validado pelo ESBMC-Python.

  2. Comparar 5 modelos de linguagem (3 LLMs via API + 2 SLMs locais)
     com o mesmo prompt — avaliação cross-model.

  3. Introduzir etapa de validação por AST para filtrar alucinações
     ANTES de invocar o verificador formal.

  4. Integrar ESBMC-Python como confirmador formal de hipóteses de bug,
     restringindo execução apenas aos casos sinalizados pelo modelo.

  5. Comparar 3 fluxos: só ESBMC (Flow A), híbrido (Flow B), só modelo (Flow C).

  6. Medir impacto da confirmação formal via Precisão, Revocação,
     F1, TCF e TRN.

O que já existe — e onde está a lacuna

[COLUNA 1 — LLMs em análise de código]
• PrimeVul [Ding et al., 2025]: F1 = 3,09% em vulnerabilidades reais
  → modelos falham em cenários complexos e representativos
• LLMs sensíveis a renomeações de variáveis → achados inconsistentes
  [Ullah et al., 2024]
• DeepSeek-R1 com contexto extra de execução: F1 ≈ 0,6, mas pode
  revisar análise correta e chegar a conclusão errada [Li et al., 2026]

[COLUNA 2 — Verificação formal de Python]
• ESBMC-Python [Farias et al., 2024]: verifica Python DIRETAMENTE
  via AST + inferência de tipos, sem traduzir para outra linguagem
• EVA [Shivaji et al., 2026] e PyVeritas [Orvalho et al., 2025]:
  traduzem Python → C antes de verificar
  → risco: diferenças semânticas Python/C podem mascarar bugs

[COLUNA 3 — Integração LLM + verificação formal]
• PropertyGPT [Tihanyi et al., 2025]: LLM gera propriedades para
  contratos inteligentes (blockchain), verificador confirma
• EVA [Shivaji et al., 2026]: orquestrador LLM+verificação para Python,
  mas traduz para C e avaliou apenas 23 programas

[COLUNA 4 — Bugs vs Code Smells]
• Santos et al. [2023]: bugs e smells compartilham características
  estruturais — LLMs confundem os dois facilmente
• Souza et al. [2026]: LLMs detectam melhor smells objetivos (Long Method)
  do que categorias dependentes de contexto

[DESTAQUE — LACUNA IDENTIFICADA]
  ↳ Nenhum trabalho combina LLM + ESBMC diretamente em Python
     com filtragem de alucinações via AST, separação bugs/smells
     e dataset controlado com ground truth manual.

[LADO ESQUERDO — O QUE É BMC]

Bounded Model Checking (BMC) [Biere et al., 1999]

Técnica de verificação formal que explora o espaço de estados
de um programa até um limite finito k de execução.

Fórmula gerada:   C ∧ ¬P
  C = restrições do programa
  P = propriedade de segurança a verificar

Solver SMT analisa a fórmula:
  • SAT  → solver encontra valores concretos que violam P
           = CONTRAEXEMPLO (bug confirmado)
  • UNSAT → nenhuma violação dentro do limite k

[LADO DIREITO — FLUXO DO ESBMC-PYTHON]

Como o ESBMC-Python processa código Python [Farias et al., 2024]:

  Código Python
    ↓  Parser Python
  AST (Árvore Sintática Abstrata)
    ↓  Inferência de tipos por anotações e uso de variáveis
  Representação intermediária GOTO
    ↓  Conversão para forma SSA (Static Single Assignment)
  Fórmula lógica C ∧ ¬P
    ↓  Solver SMT
  VERIFICATION FAILED → bug confirmado + contraexemplo
  VERIFICATION SUCCESSFUL → sem violação dentro do limite k
  Timeout → inconclusivo

Flags usadas neste trabalho:
  --function            verifica só a função indicada pelo modelo
  --assign-param-nondet entradas = valores desconhecidos (simbólico)
                        → ESBMC testa TODAS as combinações de entrada
  --incremental-bmc     limite cresce gradualmente (mais eficiente)

Propriedades verificadas:
  • Divisão por zero
  • Acesso fora dos limites de lista (out of bounds)
  • Violação de asserção explícita (assert)

Referências: [Biere et al., 1999]; [Cordeiro et al., 2012];
             [Gadelha et al., 2018]; [Farias et al., 2024]

SLIDE 7 — PIPELINE PROPOSTO: AS 5 ETAPAS
Tempo: ~2.5 minutos
[IMAGEM: diagrama_pipeline.png — coluna direita ou abaixo]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Pipeline híbrido em 5 etapas sequenciais:

[PREPROCESS] → [LLM ANALYZER] → [AST VALIDATION] ─→ [ESBMC] → [REPORT]
                                        │
                                        └─→ smells e bugs não verificáveis
                                             vão DIRETO ao Report

─────────────────────────────────────────────────────────────────
ETAPA 1 — PREPROCESS
• Cada arquivo Python é carregado individualmente
• O módulo ast do Python converte o código em AST (Árvore Sintática Abstrata)
  → representa funções, variáveis, operações e suas posições no código
• A AST é usada INTERNAMENTE na validação — NÃO é enviada ao modelo
  → Intencional: enviar a AST ao modelo revelaria a estrutura exata,
    introduzindo viés nos resultados

─────────────────────────────────────────────────────────────────
ETAPA 2 — LLM ANALYZER
• Código-fonte + metadados da função → enviados ao modelo via prompt
  (nome, parâmetros, anotações de tipo, número de linhas)
• Prompt usa Chain-of-Thought (CoT): modelo raciocina passo a passo
  antes de emitir o veredito → reduz erros em tarefas de análise [Li et al., 2026]
• 6 categorias aceitas pelo pipeline:
    Bugs verificáveis:   division_by_zero · out_of_bounds · assertion_violation
    Code smells:         long_method · many_parameters · complex_conditional
• Modelo retorna JSON com schema fixo. Por hipótese:
    tipo         → "suspected_bug" ou "smell_heuristic"
    categoria    → uma das 6 acima
    verifiable   → true (bug formal) ou false (smell / não formalizável)
    explicação   → raciocínio do modelo em linguagem natural
    expressão    → trecho exato identificado no código
• JSON inválido → zero achados para a função (pipeline não interrompe)

─────────────────────────────────────────────────────────────────
ETAPA 3 — AST VALIDATION
• Verifica se cada hipótese do modelo REALMENTE EXISTE no código
• 3 fases de validação:
    1ª — correspondência direta entre hipótese e operações extraídas
         (subscripts para out_of_bounds, divisões para division_by_zero)
    2ª — normalização via ast.unparse + busca nos nós executáveis
         (tolera diferenças de formatação, exige existência real)
    3ª — para assertion_violation: compara com instruções assert presentes
• Hipóteses sem correspondência = ALUCINAÇÕES → descartadas
  → evita invocar ESBMC sobre código que o modelo inventou

  Após AST Validation, o pipeline se bifurca:
  → Code smells e bugs com verifiable=false → Report direto
  → Bugs com verifiable=true e validados pela AST → ESBMC

─────────────────────────────────────────────────────────────────
ETAPA 4 — ESBMC
• Executado sobre o arquivo Python ORIGINAL (sem modificações)
• Saídas:
    VERIFICATION FAILED + contraexemplo  →  bug CONFIRMADO (VP)
    VERIFICATION SUCCESSFUL              →  suspeita REFUTADA (FP eliminado)
    Timeout                              →  inconclusivo

─────────────────────────────────────────────────────────────────
ETAPA 5 — REPORT
• Consolida: veredito do modelo + resultado ESBMC + ground truth
• Calcula métricas por categoria e por modelo para os 3 fluxos
• Exporta JSON + frontend HTML estático

Referências: [Li et al., 2026]; [Biere et al., 1999]; [Tihanyi et al., 2025]

Três modos de execução do pipeline:

┌─────────────────────────────────────────────────────────────────┐
│ FLOW A — ESBMC Direto (linha de base formal)                    │
│                                                                 │
│  [Função Python] → [ESBMC] → [Report]                          │
│                                                                 │
│  • ESBMC executado diretamente sobre cada função                │
│  • Sem triagem prévia por modelo de linguagem                   │
│  • Papel: validar o dataset (confirma que os bugs são reais)    │
│  • Resultado: P=1,000 · R=1,000 · F1=1,000 para todos os 45    │
│               arquivos de bug (VERIFICATION FAILED confirmado)  │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ FLOW B — Híbrido (proposta principal)                           │
│                                                                 │
│  [Função] → [LLM] → [AST Valid.] → [ESBMC] → [Report]         │
│                           │                                     │
│                           └──── smells → [Report direto]       │
│                                                                 │
│  • LLM faz triagem inicial                                      │
│  • AST Validation filtra alucinações                            │
│  • ESBMC confirma ou refuta hipóteses de bug verificáveis       │
│  • Code smells vão direto ao Report (não têm contraexemplo)     │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ FLOW C — Somente Modelo (linha de base do modelo)               │
│                                                                 │
│  [Função] → [LLM] → [AST Valid.] → [Report]                    │
│                                                                 │
│  • Usa apenas LLM + AST Validation, sem confirmação formal      │
│  • Objetivo: isolar o ganho ESPECÍFICO do ESBMC                 │
│  • Referência para calcular a TRN                               │
└─────────────────────────────────────────────────────────────────┘

Por que o modelo como triagem faz sentido?
  LLM: 2–10s/função  ←→  ESBMC: 35–50s/função [Shivaji et al., 2026]
  → Com o modelo filtrando, o ESBMC só roda em funções suspeitas
  → Muito mais viável em projetos reais

Comparação dos 3 fluxos:
  Flow A = verificador sozinho (sem modelo)
  Flow C = modelo sozinho (sem verificador)
  Flow B = combinação: elimina FPs do modelo, mantém revocação, cobre smells

Referências: [Shivaji et al., 2026]; [Kaniewski et al., 2025]; [Tihanyi et al., 2025]

SLIDE 10 — MÉTRICAS: O QUE CADA UMA MEDE
Tempo: ~1.5 minutos
[IMAGEM: diagrama_metricas.png — lado direito do slide]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Quatro resultados possíveis:

  VP  → modelo acusou bug que REALMENTE EXISTE no ground truth
  FP  → modelo acusou bug que NÃO EXISTE (alarme falso)
  FN  → bug EXISTE mas modelo NÃO reportou (bug perdido)
  TN  → função LIMPA e modelo não reportou nada (acerto)
        (só conta no nível de função, não de suspeita)

Dois níveis de avaliação:
  Por suspeita: cada hipótese avaliada individualmente
    → Precisão, Revocação, F1
  Por função: função como um todo (tem bug ou não?)
    → Acurácia, MCC (permitem contar TN)

──────────────────────────────────────────────────────
Precisão    P = VP / (VP + FP)
  Dos alertas emitidos, quantos eram bugs reais?
  Alta P = poucos alarmes falsos
  Baixa P = modelo grita lobo à toa → desenvolvedor ignora todos

Revocação   R = VP / (VP + FN)
  Dos bugs reais no dataset, quantos o modelo encontrou?
  Alta R = encontrou a maioria    |  Baixa R = perdeu muitos

F1-Score    F1 = 2·P·R / (P+R)
  Combina Precisão e Revocação — penaliza quando qualquer uma é baixa
  Útil para comparar modelos com diferentes trocas entre P e R

Acurácia    Acc = (VP_f + TN_f) / total   [por função]
  CUIDADO: dataset com 45 bugs e 10 limpas → modelo que acusa tudo
  teria Acc = 81,8% sem ser útil

MCC         Coeficiente de Matthews — corrige o problema da Acurácia
  Escala: −1 (pior que aleatório) → 0 (chutar) → +1 (perfeito)
  Considera os 4 quadrantes da matriz de confusão
  MCC = −0,059 do qwen no Flow C → pior que aleatório!

TCF — Taxa de Confirmação Formal   TCF = C / (C + N)
  C = hipóteses confirmadas pelo ESBMC
  N = hipóteses não confirmadas dentro do limite
  Dos bugs enviados ao ESBMC, quantos foram confirmados?
  Alta TCF = modelo levanta boas hipóteses verificáveis

TRN — Taxa de Redução de Ruído   TRN = (FP_C − FP_B) / FP_C
  FP_C = FPs no Flow C (só modelo)  ·  FP_B = FPs no Flow B (híbrido)
  Qual proporção dos falsos positivos o ESBMC eliminou?
  TRN = 1,000 → eliminou 100% dos FPs  ·  TRN = 0 → eliminou nenhum

Referências: [Ding et al., 2025]; [Li et al., 2026]; [Gadelha et al., 2019]

SLIDE 15 — DISCUSSÃO: 4 DESCOBERTAS CENTRAIS
Tempo: ~2 minutos
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RQ1 — O ESBMC reduz falsos positivos sem afetar a revocação?

  SIM. Em todos os 5 modelos, o ESBMC reduziu FPs sem criar novos FNs.
  Isso é ESTRUTURALMENTE GARANTIDO: o verificador só age sobre hipóteses
  que o modelo já levantou → elimina FPs mas nunca recupera FNs.

  Ganho maior para SLMs:
    qwen:     FP 20 → 0   TRN=1,000  (100% dos alarmes eliminados)
    deepseek: FP  8 → 0   TRN=1,000
  Para modelos de API (menos ruído inicial):
    claude: TRN=0,750  |  gemini: TRN=0,667

  Corrobora [Tihanyi et al., 2025]: híbrido compensa tendência a falsos positivos.

─────────────────────────────────────────────────────────────────
RQ2 — A AST Validation separa alucinações de hipóteses reais?

  SIM. Captou muito mais alucinações nos SLMs:
    GPT=0 · Claude=1 · Gemini=1  →  APIs estruturalmente confiáveis
    DeepSeek=7 · Qwen=13         →  SLMs referenciam código que não existe

  Sem AST Validation, hipóteses inválidas seriam enviadas ao ESBMC
  → custo computacional desperdiçado + resultados enganosos.
  A validação é ESPECIALMENTE CRÍTICA para SLMs locais. [Ding et al., 2025]

─────────────────────────────────────────────────────────────────
RQ3 — O ESBMC recupera bugs que o modelo perdeu (FNs)?

  NÃO. Limite central do pipeline híbrido.

  deepseek: TCF=0,964 e FP=0 no Flow B (hipóteses enviadas eram boas)
  MAS o F1 ficou em 0,720 pelos 21 FNs irrecuperáveis.
  out_of_bounds: deepseek encontrou 7/18 · qwen encontrou 5/18
  → bugs não levantados pelo modelo são impossíveis de recuperar

  CONCLUSÃO: o gargalo real é a qualidade da triagem do modelo.
  SLM fraco na triagem não melhora cobertura com ESBMC. [Li et al., 2026]

─────────────────────────────────────────────────────────────────
RQ4 — Code smells seguem a mesma lógica dos bugs?

  NÃO. Smells não são propriedades executáveis → ESBMC não se aplica.
  many_parameters: F1=1,000 para todos → critério objetivo e contável
  long_method: F1=0,000 para todos → funções longas mas coesas enganam o prompt
  qwen: 95 FPs em smells sem solução via ESBMC → necessário filtro próprio

  [Souza et al., 2026]; [Santos et al., 2023]

Referências: [Tihanyi et al., 2025]; [Ding et al., 2025]; [Li et al., 2026]; [Souza et al., 2026]
