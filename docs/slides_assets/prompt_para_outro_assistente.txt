--- SLIDE 3 — CONTEXTO ---
Por que Python é difícil de analisar automaticamente?

+ Linguagem #1 no índice TIOBE em janeiro de 2026.
+ Forte adoção em web, dados, IA e computação científica.
+ Crescimento de uso aumenta a necessidade de detecção automática.

- Tipagem dinâmica dificulta inferência precisa de propriedades.
- Análise estática tradicional pode perder comportamentos de execução.

Desafio: detectar defeitos sem transformar todo alerta em ruído.

Referências: TIOBE (2026); Farias et al. (2024).

--- SLIDE 4 — PROBLEMA ---
[Layout dois blocos lado a lado]

BLOCO ESQUERDO — LLMs para código:
+ Identificam padrões suspeitos.
+ Cobrem bugs e code smells.
+ Triagem rápida: 2–10s por função.
- Produzem falsos positivos e alucinações.
- Sem garantia formal.
- PrimeVul: F1 = 3,09% em vulnerabilidades reais (Ding et al. 2025).

BLOCO DIREITO — ESBMC-Python:
+ Verifica Python diretamente.
+ Confirma bugs com contraexemplos concretos.
+ P=1,000 quando detecta.
- Não faz triagem inicial.
- Custo alto: 35–50s por função.
- Não confirma code smells.

Referências: Ullah et al. (2024); Ding et al. (2025); Farias et al. (2024).

--- SLIDE 5 — QUESTÃO DE PESQUISA E OBJETIVOS ---
"Como combinar modelos de linguagem e verificação formal para
aumentar a confiabilidade da detecção automática de defeitos em
programas Python, reduzindo falsos positivos e diferenciando
bugs executáveis de code smells?"

Objetivos:
- Construir dataset com bugs, smells e casos limpos (ground truth manual).
- Comparar 5 modelos (LLMs via API + SLMs locais) com mesmo prompt.
- Filtrar alucinações via AST antes da verificação formal.
- Usar ESBMC-Python como confirmador formal de bugs verificáveis.
- Comparar Flow A (ESBMC direto), Flow B (híbrido), Flow C (só modelo).
- Medir P, R, F1, TCF e TRN.

--- SLIDE 6 — TRABALHOS CORRELATOS E LACUNA ---
LLMs na análise de código:
- PrimeVul: F1 = 3,09% em vulnerabilidades reais.
- LLMs variam com prompt, contexto e renomeação de variáveis.
- Mais contexto melhora modelos de raciocínio, mas não elimina erros.

Verificação de Python:
- ESBMC-Python: verifica Python diretamente via AST + inferência de tipos.
- EVA e PyVeritas: traduzem Python para C (risco semântico).

Integração LLM + verificação formal:
- PropertyGPT: LLM gera propriedades para contratos inteligentes.
- EVA (Shivaji et al. 2026): mais próximo, mas traduz para C, avaliou 23 programas.

Lacuna: nenhum trabalho combina LLM + AST Validation + ESBMC direto em Python,
separando bugs executáveis de code smells, com dataset controlado.

Referências: Ding et al. (2025); Li et al. (2026); Shivaji et al. (2026); Tihanyi et al. (2025).

--- SLIDE 7 — BMC E ESBMC-PYTHON ---
[SLIDE NOVO — NÃO EXISTIA AINDA]

Bounded Model Checking (BMC):
- Verifica propriedades dentro de limite finito k.
- Fórmula: C ∧ ¬P  (C = restrições do programa · P = propriedade)
- SAT → solver SMT encontra contraexemplo concreto.
- UNSAT → sem violação dentro do limite k.

Fluxo interno do ESBMC-Python:
Código Python → AST → inferência de tipos → GOTO → SSA → fórmula SMT → solver

Flags usadas neste trabalho:
  --function             verifica só a função indicada pelo modelo
  --assign-param-nondet  entradas = valores desconhecidos (exploração simbólica)
  --incremental-bmc      limite cresce gradualmente (mais eficiente)

Saídas:
  VERIFICATION FAILED + contraexemplo → bug confirmado
  VERIFICATION SUCCESSFUL             → suspeita refutada
  Timeout                             → inconclusivo

Referências: Biere et al. (1999); Cordeiro et al. (2012); Farias et al. (2024).

--- SLIDE 8 — PIPELINE HÍBRIDO EM 5 ETAPAS ---
[Diagrama: Preprocess → LLM Analyzer → AST Validation → ESBMC → Report]
[Seta alternativa: de AST Validation → Report para smells e bugs não verificáveis]

1. Preprocess: carrega função Python; gera AST internamente (não enviada ao modelo).
2. LLM Analyzer: código + metadados → JSON fixo (tipo, categoria, verifiable, explicação).
   Chain-of-Thought: modelo raciocina antes de emitir veredito.
   6 categorias aceitas: division_by_zero | out_of_bounds | assertion_violation
                         long_method | many_parameters | complex_conditional
3. AST Validation: cruza variável + operação + função com AST real.
   Hipóteses sem correspondência = alucinações → descartadas.
4. ESBMC: só para bugs verificáveis validados pela AST.
   --assign-param-nondet: explora todas as entradas simbolicamente.
5. Report: consolida LLM + ESBMC + ground truth. Calcula métricas.

Code smells e bugs com verifiable=false vão direto ao Report.

Referências: Biere et al. (1999); Cordeiro et al. (2012); Tihanyi et al. (2025).

--- SLIDE 12 — MÉTRICAS: O QUE CADA UMA MEDE ---
[Layout: matrix de confusão à esquerda, fórmulas à direita]

Por suspeita (bugs + smells):
  P = VP/(VP+FP)       Dos alertas emitidos, quantos eram reais?
  R = VP/(VP+FN)       Dos bugs reais, quantos foram encontrados?
  F1 = 2·P·R/(P+R)    Equilíbrio entre P e R.

Por função (usa TN dos casos limpos):
  Acurácia             Proporção de funções classificadas corretamente.
  MCC: −1 (péssimo) → 0 (aleatório) → +1 (perfeito). Robusto ao desbalanceamento.

Específicas do híbrido:
  TCF = C/(C+N)           Das hipóteses no ESBMC, quantas confirmadas?
  TRN = (FP_C−FP_B)/FP_C  Quanto ruído o ESBMC eliminou?
  TRN=1,000 → eliminou tudo · indefinida quando FP_C=0.

Referências: Ding et al. (2025); Li et al. (2026); Tihanyi et al. (2025).

--- SLIDE 18 — DISCUSSÃO: 4 DESCOBERTAS CENTRAIS ---
RQ1 — ESBMC reduz FPs sem afetar revocação?
Sim. Estruturalmente garantido: verificador só age em hipóteses levantadas.
Qwen e DeepSeek TRN=1,000. (Tihanyi et al. 2025)

RQ2 — AST Validation separa alucinações?
Sim. GPT=0; Claude=1; Gemini=1; DeepSeek=7; Qwen=13.
Crítica especialmente para SLMs locais. (Ding et al. 2025)

RQ3 — ESBMC recupera FNs que o modelo perdeu?
Não. DeepSeek: TCF=0,964 e FP=0, mas F1=0,720 pelos 21 FNs.
O gargalo é a qualidade da triagem inicial. (Li et al. 2026)

RQ4 — Code smells seguem a mesma lógica dos bugs?
Não. Smells não têm contraexemplo formal. many_parameters F1=1,000;
long_method F1=0,000; Qwen 95 FPs sem correção possível. (Souza et al. 2026)

--- SLIDE 19 — LIMITAÇÕES ---
- Dataset pequeno e controlado: 70 funções isoladas, não código de produção.
- 3 casos inconclusivos no ESBMC dentro do limite configurado.
- Híbrido só verifica hipóteses levantadas pela LLM.
- SLMs rodaram em CPU sem GPU (latência alta, não representa produção).
- long_method: critério de 20 linhas pode não capturar toda a subjetividade.
- Sem avaliação estatística formal; bootstrap fica para V2.
- Smells dependem de julgamento heurístico, sem confirmação formal.

--- SLIDE 20 — CONCLUSÃO ---
LLM para suspeitar.
AST para filtrar alucinações.
ESBMC para confirmar bugs executáveis.

Resultados principais:
- Confirmação formal reduziu FPs em todos os modelos com ruído.
- Claude Flow B: F1=0,990, superando ESBMC puro (F1=0,968).
- Qwen: maior ganho relativo de precisão (0,630 → 1,000 com ESBMC).
- ESBMC não recupera FNs; gargalo é a triagem inicial.
- long_method: zero detecção nos 3 melhores modelos.

Diferenciais vs EVA (Shivaji et al. 2026):
1. Verifica Python diretamente, sem traduzir para C.
2. Filtra alucinações via AST antes da verificação formal.
3. Trata bugs e smells em fluxos separados.
4. Dataset 70 casos com ground truth manual + validação ESBMC.

Próximos passos: dataset V2, bootstrap, filtro para smells,
uso dos contraexemplos ESBMC para validar comportamento Python.
